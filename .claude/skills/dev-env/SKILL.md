# Development environment

Grist is an Expo SDK 57 app (`apps/mobile`) in an npm-workspaces monorepo.
`expo-video` background audio and PiP come from config plugins, so Expo Go
cannot run it: you build and install the debug app yourself with
`expo run:ios` / `expo run:android`. `expo-dev-client` is **not** a dependency
today - adding it is tracked in its own issue - so there is no dev-client launcher
UI and no `--dev-client` flag anywhere below. `apps/mobile/ios` and
`apps/mobile/android` are gitignored and regenerated by prebuild.

Work through the checklist below in order. Each step is *check first, install
only what is missing*.

## 1. Node 22

```
node -v            # want v22.x
```

Install with nvm if missing: `nvm install 22 && nvm use 22`. In non-interactive
shells (agents, scripts) the `nvm` shell function can hang - call the binary
directly, e.g. `~/.nvm/versions/node/v22*/bin/node`.

Then, from the repo root:

```
npm ci
```

Always root, never `apps/mobile`: the workspaces hoist. The repo `.npmrc` pins
`registry.npmjs.org`. If the public registry is blocked on your machine, set
`npm_config_registry` to your organisation's mirror for the install command only
and never commit a `package-lock.json` whose URLs point at it - diff the lockfile
before committing.

## 2. iOS toolchain

```
xcodebuild -version          # Xcode installed and licensed
xcrun simctl list devices available | grep 'iPhone 17 Pro'
```

Install Xcode from the App Store, then `sudo xcodebuild -license accept` and
`xcode-select --install`. Create the simulator if it is not listed:

```
xcrun simctl create "iPhone 17 Pro" com.apple.CoreSimulator.SimDeviceType.iPhone-17-Pro
```

We standardise on iPhone 17 Pro so Maestro screenshots are comparable.

## 3. Java 21

Gradle in SDK 57 breaks on newer JDKs. Pin 21. Java 21 with `platforms;android-35`
and `build-tools;35.0.0` is the combination verified on the maintainer's machine:
it builds and runs. Treat any other combination as untested.

```
java -version                # want 21.x
brew install openjdk@21
```

```
export JAVA_HOME="$(brew --prefix openjdk@21)/libexec/openjdk.jdk/Contents/Home"
export PATH="$JAVA_HOME/bin:$PATH"
```

## 4. Android SDK

```
brew install --cask android-commandlinetools
```

```
export ANDROID_HOME="$(brew --prefix)/share/android-commandlinetools"
export PATH="$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$ANDROID_HOME/cmdline-tools/latest/bin:$PATH"
```

Put the four exports (JAVA_HOME, ANDROID_HOME, and the two PATH lines) in your
shell profile.

```
sdkmanager --licenses
sdkmanager "platform-tools" "platforms;android-35" "build-tools;35.0.0" "emulator" "system-images;android-35;google_apis;arm64-v8a"
```

Create the AVD once:

```
avdmanager create avd -n grist_pixel8 -k "system-images;android-35;google_apis;arm64-v8a" -d pixel_8
emulator -avd grist_pixel8 &
adb devices                  # expect emulator-5554  device
```

## 5. Maestro

```
curl -fsSL "https://get.maestro.mobile.dev" | bash
~/.maestro/bin/maestro --version
```

Add `~/.maestro/bin` to PATH. The flows live in `apps/mobile/.maestro/`.

## 6. EAS

```
npx eas-cli whoami || npx eas-cli login
```

The project is already linked through `expo.extra.eas.projectId` in
`apps/mobile/app.json`. Do not run `eas init`; it would relink and rewrite that
id.

`apps/mobile/eas.json` has three build profiles:

- `preview` - internal distribution: an Android APK, an ad-hoc iOS build.
- `production` - store builds, `autoIncrement` on.
- `development` - `developmentClient: true`, so it only works once `expo-dev-client` is a dependency. Leave it alone until then.

A local APK without the EAS queue:

```
cd apps/mobile
eas build --platform android --profile preview --local
```

## Running the app

Metro starts from `apps/mobile`, never the repo root:

```
cd apps/mobile
npx expo start --port 8081 -c
```

Build and install the debug app (first run, and after any native config or
plugin change):

```
cd apps/mobile
npx expo run:ios                        # builds, installs, launches on the sim
npx expo run:android --no-bundler       # Metro is already running
```

`--no-bundler` keeps Gradle from starting a second Metro on another port.

The debug app reads the bundle from `localhost:8081`, so on Android forward the
port and launch the activity:

```
adb reverse tcp:8081 tcp:8081
adb shell am start -n com.asafrose.grist/.MainActivity
```

Re-run `adb reverse` after every emulator reboot and after an `adb` restart.

## Emulator and simulator quirks

- `adb` reports `device offline` for a while after boot. `adb kill-server && adb start-server`, then wait for `adb wait-for-device`.
- Gboard shows a stylus-handwriting popup that steals taps from Maestro: `adb shell settings put secure stylus_handwriting_enabled 0`.
- With more than one target attached, Maestro needs to be told which: `--device emulator-5554` (iOS sims are addressed by their `simctl` UDID).
- Maestro drives the installed debug build. Rebuild after a native change or the flows test stale native code.
- Never edit the working tree while a suite runs. Fast Refresh reloads the app mid-flow and the driver loses it.

## Verify

All five commands below must exit 0 before you call the machine ready. Run the
first three from the worktree root.

```
npm run lint                   # repo root: custom greps + oxlint + oxfmt --check
npm test                       # workspaces; apps/mobile runs jest --coverage with per-file gates
npm run typecheck              # tsc --noEmit in each workspace
```

Then, with Metro running and the debug app installed on both targets:

```
cd apps/mobile
maestro test .maestro          # iOS: the whole directory in one run
./scripts/maestro-android.sh   # Android: one flow at a time, retries on "device offline"
```

Android cannot run the directory in one go reliably - `adb` drops to `device
offline` between flows - so the script iterates `.maestro/*.yaml` against
`emulator-5554`, restarts adb and re-runs `adb reverse` before retrying a flow
once, and prints `[Passed]` / `[Failed]` per flow.

The flows sign in through the demo fixtures (`demo-sign-in`), so no real token
is needed. Rerun a single failing flow before treating it as a real failure.
